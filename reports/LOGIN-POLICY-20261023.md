# Защита входа: 23.10.2026

**История первоначальной настройки на 900 секунд.** Позднее блокировка fixed сокращена до 15 секунд при прежнем окне 900 секунд и пороге 3. Текущая проверка и команды: [LOGIN-BLOCK15-20261023.md](LOGIN-BLOCK15-20261023.md). Данные запусков ниже сохранены без изменения.

## Fixed

Три последовательных неверных пароля одного аккаунта в скользящем окне 900 секунд устанавливают блокировку на 900 секунд. Третий ввод возвращает обычную ошибку входа (200); четвёртый и последующие — 429, включая правильный пароль. Retry-After — округлённое вверх оставшееся время. Заблокированные запросы не продлевают срок. Успех до порога сбрасывает ошибки. CSRF проверяется раньше и не считается неверным паролем.

Состояние хранится в SQLite: новая таблица login_failure_events содержит времена ошибок, login_attempts — блокировку. BEGIN IMMEDIATE сериализует проверку пароля и изменение состояния между процессами. Cookie/IP не определяют аккаунт; новые сессии не обходят блокировку. Старый независимый source-бюджет fixed заменён требуемой политикой по аккаунту: иначе успешный вход не сбрасывал бы все причины блокировки. Ограничение по источнику остаётся отдельной функцией nginx на 8081. Неизвестные аккаунты проходят аналогичную проверку с фиктивным хешем.

Таблица добавлена через CREATE TABLE IF NOT EXISTS; пользовательские записи не удалялись. CLI reset-login-limits очищает обе служебные таблицы, но при проверке сброс не запускался.

## Причина пропуска WAF и исправление

Фактический nginx -T подтвердил подключение login-rate.conf в http, ключ POST:/login → $realip_remote_addr, rate=12r/m, burst=4 nodelay, отсутствие включённого dry-run и proxy_pass http://vulnerable:5000. Логи показывают одного peer 172.18.0.1 и PASSED. POST исходного скрипта приходили через 8–9 секунд: 09:43:57, 09:44:06, 09:44:14 UTC и далее. Старый бюджет восстанавливался каждые 5 секунд: последовательный скрипт не превышал заданную скорость. Причина клиентских задержек отдельно не исследовалась.

Новый механизм — **nginx limit_req**, не ModSecurity: **2r/m, burst=2 nodelay**, dry-run явно off. Ключ — первоначальный TCP peer, не поддельные заголовки, User-Agent, пароль или маркер скрипта. Только POST /login расходует бюджет. Первые три быстрые попытки могут пройти; последующие ограничиваются. Retry-After=90 — консервативная рекомендация дождаться восстановления бюджета, не фактический таймер аккаунта. Это не блокировка после трёх неправильных паролей на 15 минут. Медленный перебор ниже скорости остаётся ограничением механизма; пользователи за общим IP разделяют бюджет.

- `waf-before.txt`: исходный bruteforce_demo.py подтвердил пропуск десяти попыток до изменения.

## Команды повторения

Из корня проекта, после естественного окончания предыдущих ограничений:

```powershell
docker compose up -d --build --no-deps --wait fixed
docker compose up -d --no-deps --force-recreate --wait waf
.\.venv\Scripts\python.exe bruteforce_demo.py vulnerable
.\.venv\Scripts\python.exe bruteforce_demo.py waf
# Через 90 секунд после последнего запроса WAF:
.\.venv\Scripts\python.exe bruteforce_demo.py waf --check
.\.venv\Scripts\python.exe bruteforce_demo.py fixed
# Через 900 секунд после третьего неверного ввода:
.\.venv\Scripts\python.exe bruteforce_demo.py fixed --check
.\.venv\Scripts\python.exe -m unittest discover -s tests -p login_limit_checks.py -v
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/run-local-sast.ps1 fixed -RecreateDatabase
```

Demo fixed останавливается на четвёртом неверном вводе. Отдельный HTTP-тест проверил именно четвёртый правильный пароль. Для проверки трёх вариантов без очистки комментариев также доступен `tests/bruteforce.py --report-dir <новая-папка>`; он создаёт попытки входа, поэтому запускай его после окончания текущих ограничений.
