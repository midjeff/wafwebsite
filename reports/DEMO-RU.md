# Сценарий защиты: 7–10 минут

Актуальная подробная инструкция после доработки каталога документов и повторного CodeQL: [TUTORIAL-RU.md](TUTORIAL-RU.md). Ниже сохранён более ранний сценарий; его числа проверок и описание защиты путей относятся к предыдущему состоянию проекта.

## Подготовка до занятия

Запустите Docker Desktop, затем:

```powershell
cd C:\Users\Shwepes\wafwebsite
.\scripts\lab.ps1 start
.\scripts\lab.ps1 reset
.\scripts\lab.ps1 test
.\scripts\lab.ps1 reset
.\scripts\lab.ps1 sonar
# Первичная настройка и token — SONAR-SETUP.md
.\scripts\lab.ps1 scan
```

Проверка 22.10.2026: Docker установлен, приложения и WAF запущены; `test` дал 54/54 HTTP и 5/5 audit PASS. Ping исправлен снятием файловой capability, ограничения контейнеров сохранены. Сеть lab имеет internal: false, порты опубликованы только на 127.0.0.1. SonarQube и исполнение JavaScript в браузере ещё не проверены. Результаты Semgrep остались прежними: Registry 0/0, custom 5/1. Перед защитой повторите демонстрацию; фактические правила и история исправлений — в VERIFICATION.md.

Подготовьте окна: обычный профиль — Алиса; приватный профиль — Борис. Откройте 8080, 8081, 8082 и SonarQube. Учтите: 8080/8081 одного профиля разделяют cookie и одну БД. На 8082 отдельная cookie. Желательно масштаб браузера 110–125% для проектора.

Учётные данные: `alice / Alice-Lab-2026!`, `bob / Bob-Lab-2026!`.

## 0:00–1:00 — Архитектура и обычная работа

Покажите обзор 8080, таблицу заявок, сотрудника Алису и инструкцию. Создайте обычную заявку. Объясните: «8080 — напрямую; 8081 — тот же backend и та же SQLite через ModSecurity; 8082 — исправленный код и отдельная БД без WAF». Откройте созданную заявку через 8081: это также демонстрирует общую БД.

На `/lab` находятся учебные строки. Открытие этой страницы ничего не атакует.

## 1:00–2:00 — SQL Injection

1. На 8080 в «Сотрудники» найдите `Алиса`: одна карточка.
2. Введите строку, сохраняя пробел после `--`:

```text
' OR 1=1 -- 
```

3. На уязвимой версии должны появиться четыре карточки.
4. Повторите на 8081: ожидается 403. Сохраните фактический результат.
5. Повторите на 8082: ноль совпадений, запрос не меняет SQL-структуру.

Фраза: «В исправленном коде значение передаётся параметром, поэтому кавычки остаются данными».

## 2:00–2:45 — Reflected XSS

В «Сотрудники» → «Личное приветствие» на 8080 введите:

```html
<script>alert("LAB_XSS")</script>
```

Зафиксируйте реальный диалог `LAB_XSS` и закройте его. Повторите ввод через 8081 (ожидается блокировка) и 8082 (буквальный текст, без диалога).

Фраза: «`safe` отключал экранирование. Исправление — контекстное HTML-экранирование Jinja. CSP добавлена, но основной причиной устранения XSS является безопасный вывод».

## 2:45–4:15 — Stored XSS двумя пользователями

Перед **каждым** из трёх вариантов выполните:

```powershell
.\scripts\lab.ps1 clean-comments
```

1. На 8080 Алиса открывает `/tickets/1003` и сохраняет комментарий:

```html
<script>alert("LAB_STORED")</script>
```

2. Алиса тоже может увидеть alert сразу после отправки; закройте его.
3. В отдельном приватном окне Борис открывает 8080 `/tickets/1003`: alert подтверждает сохранение и исполнение для другого пользователя.
4. Очистите комментарии. На 8081 Алиса отправляет тот же комментарий: ожидается блокировка **POST**. Борис обновляет #1003: учебный payload не должен быть сохранён.
5. Снова очистите комментарии. На 8082 Алиса отправляет строку, Борис открывает общую заявку: видит текст `<script>…</script>`, исполнения нет.

Фраза: «Оба участника имеют право на общую заявку. Этот сценарий не зависит от IDOR. WAF не удаляет старые записи, поэтому перед тестом нужна очистка».

## 4:15–5:00 — Command Injection

В «Диагностика» сначала проверьте `127.0.0.1`, затем в Linux-контейнере:

```text
127.0.0.1; echo LAB_TEST
```

На 8080 дополнительная строка `LAB_TEST` должна находиться **в выводе терминала**, а не просто в поле ввода. На 8081 ожидается блокировка. На 8082 — 400: значение не является IP-адресом, shell не используется.

Фраза: «Контейнер работает на Linux, даже если управляющие команды запускаем в PowerShell. Время и вывод ограничены, пользователь контейнера не root. Это уменьшает последствия, но само по себе не исправляет инъекцию».

## 5:00–5:40 — Path Traversal

После входа откройте:

```text
http://localhost:8080/download?file=..%2Flab-only.txt
http://localhost:8081/download?file=..%2Flab-only.txt
http://localhost:8082/download?file=..%2Flab-only.txt
```

На 8080 должен быть `LAB_TRAVERSAL_PROOF`, на 8081 ожидается блокировка, на 8082 — 400. Покажите, что обычный файл `onboarding.txt` по-прежнему доступен.

Фраза: «Файл специально создан вне documents, настоящих секретов нет. Исправление проверяет итоговый канонический путь, а не только наличие подстроки `../`».

## 5:40–6:30 — IDOR и граница возможностей WAF

1. Алиса открывает `/tickets/1001`.
2. Меняет номер на `/tickets/1002` — видит тестовую заявку Бориса и `BOB_PRIVATE`.
3. Через 8081 обычный запрос к чужому ID ожидаемо проходит: WAF не знает владельца.
4. На 8082 Алисе — 403. В приватном окне Борис открывает ту же заявку успешно.

Фраза: «Знать, кто вошёл, недостаточно. Сервер обязан проверить доступ именно к этому объекту. Номер заявки нельзя считать секретом».

## 6:30–7:15 — Журнал настоящего WAF

```powershell
.\scripts\lab.ps1 logs
```

Откройте `logs/waf.log` и `reports/generated/waf-evidence.json`. Выберите транзакцию с `lab_case`, покажите ответ 403, **реальный** ID правила и `msg`. Поясните отличие детектирующего правила от финальной оценки anomaly score. Номер правила заранее в этом сценарии не выдумывается.

## 7:15–9:15 — SAST, исправления и повторная проверка

Покажите два проекта SonarQube, если они фактически просканированы. Отдельно откройте Issues и Security Hotspots; не называйте замечание о сложности доказанной уязвимостью. Если SonarQube не запускался, честно покажите конфигурацию и статус NOT RUN.

Покажите `reports/generated/semgrep-summary.json`:

- готовый p/python: **0 / 0**;
- авторские учебные правила: **5 / 1**;
- оставшееся предупреждение пути: ручной разбор и проверки показывают containment; предупреждение не скрыто;
- IDOR: автоматически не найден, подтверждён двумя сессиями.

Сопоставьте SQL f-string с параметризованным запросом, `safe` с автоэкранированием, shell-строку со списком аргументов, проверку пути и проверку владельца. Завершите реальными PASS/FAIL из тестового JSON.

Финальная фраза: «SAST помогает найти опасные конструкции, WAF снижает риск некоторых запросов, а исправление кода устраняет причины. Отсутствие предупреждений не доказывает безопасность — поэтому есть проверки поведения».

