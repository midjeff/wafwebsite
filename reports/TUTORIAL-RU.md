## 1. Что именно мы показываем

NEXUS — небольшой корпоративный портал поддержки. Пользователь входит под своим аккаунтом, видит заявки, создаёт их, пишет комментарии, ищет сотрудников, читает инструкции и запускает ping.

Есть две реализации сайта и три входа:

```text
Браузер → 127.0.0.1:8080 → vulnerable (Flask + Waitress) → своя SQLite
Браузер → 127.0.0.1:8081 → nginx + ModSecurity/OWASP CRS → тот же vulnerable
Браузер → 127.0.0.1:8082 → fixed (Flask + Waitress)      → отдельная SQLite
```

Flask связывает адреса с Python-функциями. Waitress принимает HTTP-запросы. SQLite хранит пользователей, заявки и комментарии. Шаблоны Jinja собирают HTML, CSS оформляет страницы. WAF — отдельный фильтрующий reverse proxy перед vulnerable. Исправления fixed работают без WAF.

Порты опубликованы только на `127.0.0.1`. Сеть `lab` имеет `internal: false`. Приложения работают как UID/GID 10001, с `cap_drop: ALL` и `no-new-privileges`. Дополнительный SonarQube работает на порту 9000, хранит данные вместе с PostgreSQL в Docker volumes. CodeQL и Bandit анализируют локальные файлы; контейнеры сайта для их запуска не нужны.

Фраза для защиты: «Я сравниваю уязвимый код напрямую, тот же код за WAF и исправленный код без WAF. Так видно различие между блокировкой запроса и устранением причины».

## 2. Подготовить и запустить

1. Открой Docker Desktop и дождись готовности Engine. Нужен режим Linux containers.
2. Открой терминал PowerShell в VS Code: **Terminal → New Terminal**.
3. Выполняй команды по одной:

```powershell
cd C:\Users\Shwepes\wafwebsite
docker version
docker compose version
docker info --format '{{.OSType}}'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\lab.ps1 start
docker compose ps
```

Ожидается `linux`, затем три сервиса vulnerable/fixed/waf со статусом healthy. Первый запуск может загружать образы. `Bypass` действует только на этот процесс PowerShell. После изменения исходников нужен новый образ: обычное обновление страницы не копирует Python-файлы в контейнер.

Открой в браузере:

```text
http://127.0.0.1:8080/login
http://127.0.0.1:8081/login
http://127.0.0.1:8082/login
```

Для всех ручных действий используй один вид адреса: в этом руководстве это `127.0.0.1`. Не переключайся между ним и `localhost` посреди сессии: браузер считает их разными хостами.

Учебные аккаунты:

| Кто | Логин | Пароль | Своя заявка |
|---|---|---|---|
| Алиса | `alice` | `Alice-Lab-2026!` | 1001 |
| Борис | `bob` | `Bob-Lab-2026!` | 1002 |

Заявка 1003 общая, 1004 принадлежит Алисе. Имена и пароли учебные; хеши хранятся в БД. Пароль администратора SonarQube и токен анализа — другие секреты: не выводи их на проектор и не включай в скриншоты.

Алису открой в обычном профиле браузера, Бориса — в приватном окне или отдельном профиле. Две обычные вкладки одного профиля не дают двух независимых пользователей. Порты 8080 и 8081 разделяют cookie и одну БД; у 8082 другое имя cookie и другая БД.

## 4. Сначала показать обычную работу

На 8080 войди как Алиса. Открой список заявок и 1001; создай обычную заявку с темой «Проверка перед защитой», выбрав категорию и приоритет. Затем открой 8081 и найди эту же заявку: так демонстрируется общая БД vulnerable и WAF. На 8082 этой новой заявки не будет — там отдельная БД.

В «Сотрудники» найди `Алиса`: должна появиться одна карточка. В «Базе знаний» открой и скачай все три инструкции: onboarding, vpn, meetings. В «Диагностике» запусти `127.0.0.1`: должен быть ответ ping. Проверь это также на fixed.

Дополнительная проверка ping через терминал:

```powershell
docker compose exec -T vulnerable ping -c 1 -W 2 127.0.0.1
docker compose exec -T fixed ping -c 1 -W 2 127.0.0.1
```

Оба контейнера — Linux, хотя терминал Windows. Ранее ping не запускался из-за файловой capability при пустом наборе capabilities контейнера. Общий Dockerfile снимает её командой `RUN /usr/sbin/setcap -r /usr/bin/ping`; разрешён непривилегированный ping через `ping_group_range`. NET_RAW и root не понадобились.

## 5. Шесть атак: ввод → результат → объяснение

Для каждого опыта войди как Алиса на нужном порту. Ожидания относятся к штатным учебным данным и действующей конфигурации; при расхождении запиши фактический результат и проверь журнал.

### 5.1. SQL Injection — поиск сотрудников

Открой `/employees`. В поле поиска сначала введи `Алиса`, потом следующую строку; после двух дефисов есть пробел:

```text
' OR 1=1 -- 
```

Ожидание: 8080 — четыре сотрудника вместо одного; 8081 — блокировка 403; 8082 — ноль совпадений. Покажи `app/main.py`, `employees()`: пользовательский текст вставляется в SQL через f-string. Затем `app-fixed/main.py`, `employees()`: SQL содержит `?`, значение передаётся отдельно.

Объяснение: «В vulnerable ввод меняет условие SQL. В fixed он остаётся значением поиска».

Необязательная демонстрация утечки учебных хешей, в том же поле на 8080:

```text
' AND 1=0 UNION SELECT id, username, password_hash, email, initials FROM users -- 
```

В карточках появляется хеш вроде `scrypt:...`. Это **не исходный пароль**; SQLi раскрывает сохранённые данные, а в БД лежат хеши. На fixed запрос не должен раскрывать эти значения. Для короткой защиты достаточно первого примера.

### 5.2. Reflected XSS — личное приветствие

На странице сотрудников внизу найди форму «Личное приветствие». Введи:

```html
<script>alert("LAB_XSS")</script>
```

8080 — диалог `LAB_XSS`, его нужно закрыть. 8081 — ожидается 403. 8082 — текст отображается буквально, диалога нет.

Код: `greeting()` получает `name`; в `app/templates/greeting.html` есть `{{ name|safe }}`, в fixed — `{{ name }}`. `safe` разрешал трактовать ввод как HTML. Fixed возвращает автоматическое экранирование; CSP даёт дополнительную защиту.

Объяснение: «Ввод вернулся в ответ и исполнился в браузере. В БД для этого опыта ничего не сохраняется».

### 5.3. Stored XSS — комментарий для другого пользователя

Нужны Алиса и Борис в разных профилях. Перед каждым вариантом очисти общую заявку. Следующая команда **заменяет все комментарии 1003 в обеих БД двумя исходными** — сначала сохрани свои записи, если они нужны:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\lab.ps1 clean-comments
```

1. На 8080 Алиса открывает `/tickets/1003` и отправляет комментарий:

```html
<script>alert("LAB_STORED")</script>
```

2. Закрой диалог у Алисы. Борис открывает ту же заявку на 8080: диалог появляется у него — значит, строка сохранилась и исполнилась у другого пользователя.
3. Очисти комментарии. Повтори отправку на 8081: ожидается блокировка POST и отсутствие нового payload у Бориса.
4. Очисти комментарии. Повтори на 8082: комментарий сохраняется как текст, Борис видит строку, но скрипт не исполняется.

Код: `ticket()` сохраняет комментарий параметризованным INSERT; источник XSS — последующий вывод `comment.body|safe` в `app/templates/ticket.html`. В fixed используется `{{ comment.body }}`.

Объяснение: «Безопасный SQL не гарантирует безопасный HTML. WAF не удаляет уже сохранённые опасные комментарии: открытый через 8081 старый payload может исполниться, потому что backend и БД общие».

### 5.4. Command Injection — диагностика

Открой `/diagnostics`. Сначала запусти `127.0.0.1`, затем введи:

```text
127.0.0.1; echo LAB_TEST
```

8080 — в блоке **вывода процесса** появляется отдельная строка `LAB_TEST`. Её наличие в поле ввода не считается доказательством. 8081 — ожидается 403. 8082 — 400, поскольку строка не является IP-адресом.

Код: vulnerable `diagnostics()` объединяет host со строкой команды и вызывает `bounded_run(..., shell=True)`; `app/process.py` передаёт это в `Popen`. Fixed разбирает IP через `ipaddress`, разрешает только loopback, передаёт список аргументов; в `app-fixed/process.py` жёстко указано `shell=False`, параметра для включения shell больше нет.

Объяснение: «В vulnerable оболочка считает точку с запятой разделителем команд. В fixed оболочка не запускается, ввод проверяется как IP». Для Linux-контейнеров используется `;`; вариант Windows developer preview с `&` относится к другой среде.

### 5.5. Path Traversal — документ за пределами каталога

После входа открой по очереди:

```text
http://127.0.0.1:8080/download?file=..%2Flab-only.txt
http://127.0.0.1:8081/download?file=..%2Flab-only.txt
http://127.0.0.1:8082/download?file=..%2Flab-only.txt
```

8080 — учебный маркер `LAB_TRAVERSAL_PROOF`; 8081 — ожидается 403; 8082 — 400. Это чтение специально созданного безвредного файла вне `documents/`.

Код: vulnerable `download()` строит путь из `request.args['file']`. В fixed посмотри **два места**: `DOCUMENTS` в начале `main.py` и `download()`. Значение запроса только выбирает запись каталога, а путь задан сервером заранее. Данные запроса не соединяются с файловым путём.

На 8082 также проверь:

```text
/download?file=onboarding.txt                 → 200, просмотр
/download?file=vpn.txt&attachment=1           → 200, скачивание
/download?file=meetings.txt                   → 200, просмотр
/download?file=unknown.txt                    → 400
/download?file=.%2Fonboarding.txt             → 400
/download?file=%2Fsrv%2Fportal%2Fdocuments%2Fonboarding.txt → 400
```

Объяснение: «Параметр file теперь является идентификатором. Даже существующий абсолютный путь не считается разрешённым идентификатором». Старое описание fixed через `.resolve()/relative_to()` относится к прежней реализации.

### 5.6. IDOR — чужая заявка

Алиса открывает 1001, затем меняет адрес на `/tickets/1002`. В vulnerable она видит чужую заявку Бориса, включая учебный маркер `BOB_PRIVATE`. Через WAF доступ также проходит. В fixed Алиса получает 403, а Борис в своём профиле успешно открывает 1002.

Код: `app/main.py`, `load_ticket()` получает заявку по ID, но не проверяет владельца. Fixed `load_ticket()` разрешает доступ владельцу или участнику; эта функция вызывается до обработки и GET, и POST.

Объяснение: «Вход подтверждает личность. Отдельно требуется проверить право на конкретную заявку. WAF не знает бизнес-правил владельцев и участников».

## 6. Перебор паролей и полная проверка стенда

Седьмой отдельный сценарий — ограниченный перебор учебного пароля:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\lab.ps1 brute-force
```

Скрипт использует 10 заданных паролей для alice, правильный последний. Vulnerable допускает вход; WAF ограничивает частоту POST `/login` через nginx; fixed считает ошибки в SQLite и временно блокирует вход. Здесь 429 — ограничение частоты, а не правило CRS. Точные условия и прежние измерения: [BRUTE-FORCE.md](BRUTE-FORCE.md). Fixed-код — `login_limits.py`, функция `authenticate()`; nginx — `waf/login-rate.conf`.

Полный автоматический прогон:

```powershell
# Сначала сохранить старые результаты и собственные данные — см. ниже.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\lab.ps1 test
```

Команда пересобирает/пересоздаёт стенд, очищает комментарии 1003, сбрасывает лимиты входа, создаёт учебные данные, выполняет HTTP и audit-проверки, затем ограниченный brute force и очистку тестовых заявок. Это тест с изменением данных, а не просто просмотр сайта.

Сначала сохрани прежние отчёты; следующие команды только копируют их в игнорируемый локальный каталог:

```powershell
$tutorialStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$tutorialBackup = Join-Path '.runtime' "tutorial-backup-$tutorialStamp"
New-Item -ItemType Directory -Path $tutorialBackup | Out-Null
Copy-Item -LiteralPath reports/generated -Destination $tutorialBackup -Recurse
Copy-Item -LiteralPath logs -Destination $tutorialBackup -Recurse
if (Test-Path reports/screenshots) { Copy-Item -LiteralPath reports/screenshots -Destination $tutorialBackup -Recurse }
```

Это архив результатов, **не резервная копия Docker-БД**. Не запускай `reset`, `clean-comments` или полный `test`, пока не сохранил нужные записи из портала. `reset` возвращает исходные данные обеих БД. Для обычного показа сброс не обязателен.

Что означает каждый слой проверки:

| Проверка | Что доказывает | Чего не доказывает |
|---|---|---|
| HTTP | Ответ, содержимое, сохранение, доступ двух пользователей, эффект команды/чтения файла | Исполнение JavaScript в браузере |
| Audit WAF | Связь запроса с настоящим правилом и блокировкой | Сам по себе 403 ещё не доказывает срабатывание WAF |
| Браузер | Реальный диалог JavaScript, поведение UI | Отсутствие всех возможных XSS |
| SAST | Опасный поток или конструкция в исходниках | Эксплуатируемость любой находки и полную безопасность при нуле |

В полном ранее сохранённом прогоне: **72/72 HTTP**, **10/10 audit**, три сценария brute force. После последней доработки повторены **24/24 fixed HTTP**, **35/35 документов**, **37/37 локальных тестов**, структурная проверка; полный WAF/браузерный прогон после этой доработки не повторялся.

Журналы WAF и доказательства:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\lab.ps1 logs
```

Открой `logs/waf.log`, найди `lab_case` из `reports/generated/http-waf.json`, затем соответствующие `id` и `msg`. `reports/generated/waf-evidence.json` сопоставляет 10 атак с транзакциями audit. Покажи настоящее детектирующее правило и итоговое блокирование по anomaly score; не придумывай ID заранее. Ручные запросы из браузера без `lab_case` автоматически в эту таблицу не добавляются.

## 7. Дополнительные проверки без запуска всего стенда

Для локальных Python-команд используется `.venv`. Если её ещё нет:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r tests/requirements-local.txt
```

Запуск с выводом в терминал, без перезаписи старого `local-checks.json`:

```powershell

.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -p login_limit_checks.py -v
```

Первая команда проверяет обе реализации с временными SQLite-БД и реальными процессами Windows; ожидаемый текущий набор — 37 тестов. Вторая проверяет структуру и конфигурацию, но не запускает Docker. Третья отдельно проверяет лимитер, в том числе работу между процессами. Прямой CSRF-набор: `.\.venv\Scripts\python.exe -X utf8 tests/csrf_checks.py` — он перезаписывает `reports/generated/csrf-checks.json`, поэтому сначала сделай архив. В нём проверяются отсутствующий, неверный, чужой и корректный токены на fixed без WAF.

Проверить реальные ссылки документов обновлённого контейнера, создав новый отчёт:

```powershell
$documentStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
.\.venv\Scripts\python.exe -X utf8 tests/document_catalog_checks.py --base http://127.0.0.1:8082 --report "reports/generated/documents-$documentStamp.json"
```

Ожидается 35 успешных проверок. Этот набор входит, читает документы и не создаёт заявки. Другой HTTP-набор создаёт заявки и комментарии:

```powershell
$httpStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
.\.venv\Scripts\python.exe -X utf8 tests/http_checks.py --mode fixed --base http://127.0.0.1:8082 --report-dir "reports/generated/manual-fixed-$httpStamp"
```

Для него перед запуском нужна чистая 1003; при необходимости отдельно выполни осознанную очистку из раздела 5.3. Ожидается 24 проверки. Linux — правильный параметр платформы по умолчанию для контейнера.

Для автоматического браузерного теста нужны Playwright и установленный Chrome. После архивации результатов:

```powershell
.\.venv\Scripts\python.exe -m pip install playwright
.\.venv\Scripts\python.exe -X utf8 tests/browser_checks.py --channel chrome
```

Chrome должен быть установлен; скрипт сам его не устанавливает. Он **очищает комментарии 1003 обеих версий**, проверяет реальное исполнение XSS, переписывает `reports/generated/browser-checks.json` и скриншоты в `reports/screenshots/`. Ранее сохранённый результат — 25/25, новый результат оценивай по его JSON. Для ручной защиты браузерные опыты из раздела 5 также подходят.

## 8. Основная SAST-демонстрация: CodeQL → код → fixed

SAST означает анализ исходников без отправки атакующих запросов сайту. CodeQL строит базу кода и ищет потоки от источника ввода к опасной операции. Bandit дополнительно отмечает опасные Python-конструкции.

Подготовленный локальный инструмент: `.runtime/tools/codeql-bundle-v2.27.2/`. Версии закреплены в `sast/codeql-lock.json`: CLI **2.27.2**, официальный pack `codeql/python-queries` **1.8.12**, набор **python-security-extended**, 52 запроса. Если tools отсутствует после нового checkout, инструкция скачивания и проверки SHA-256 есть в [CODEQL-BANDIT-COMPARISON.md](CODEQL-BANDIT-COMPARISON.md), раздел «Повторить сканирование в Windows PowerShell».

Bandit устанавливается отдельно:

```powershell
.\.venv\Scripts\python.exe -m pip install -r sast/requirements-sast.txt
```

Сначала анализируй только vulnerable:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-local-sast.ps1 vulnerable -RecreateDatabase
```

Скрипт напечатает новую папку `reports/generated/codeql-sast/vulnerable-<дата-время>/`. Открой в ней `summary.json`, `codeql.sarif`, `bandit.json`, `metadata.json` и `source-inventory.json`. Покажи SQLi, command injection и два path-результата CodeQL, затем соответствующий код.

После разбора запусти fixed отдельно:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-local-sast.ps1 fixed -RecreateDatabase
```

Появится **другая новая папка**. `-RecreateDatabase` пересоздаёт только выбранную рабочую CodeQL-базу, прежние папки отчётов сохраняются. Скрипт запускает и CodeQL, и Bandit по выбранной версии. В нём нет custom-запросов или исключений файлов/строк ради ожидаемого счётчика.

Сохранённые результаты для сравнения:

| Результат | CodeQL | Bandit |
|---|---|---|
| `vulnerable-20261022-224555` | 4: SQLi, command injection, 2 path injection | 4: B608, B604, B404, B602 |
| `fixed-20261022-232717` — ДО последней доработки | 3 × path injection | 2: B404, B602 |
| `fixed-20261022-234453` — ПОСЛЕ доработки | **0** | **2: B404, B603**, оба Low / High confidence |

У тебя в IDE может быть открыт именно **старый** `fixed-20261022-232717/codeql.sarif` с тремя находками. Он сохранён намеренно. Актуальный нулевой результат — `fixed-20261022-234453/codeql.sarif`. Ручное редактирование SARIF не требуется.

История исправлений: SQL-параметры и отказ от shell в маршруте существовали до первых сканирований. После трёх path-предупреждений fixed дополнительно переведён на каталог серверных путей; из helper удалена возможность включать shell. Не говори, что все исправления были впервые сделаны после запуска CodeQL.

Оставшиеся Bandit: B404 указывает на импорт `subprocess`; B603 — на необходимость проверить аргументы процесса даже без shell. В текущем маршруте IP проверен, разрешён только loopback, программа/ключи задаются сервером, `shell=False`. Сигналы оставлены и разобраны, не подавлены. Ненулевой exit code Bandit 1 при находках ожидаем; ошибки разбора проверяются отдельно.

Охват: CodeQL/Bandit проверяют 4 Python-файла vulnerable и 5 fixed. Это не полный анализ шаблонов, CSS и всего проекта. В новом CodeQL-логе есть четыре сообщения `No installed Python found!` вспомогательного launcher: база успешно создана, 52 запроса выполнены, но полнота автоопределения зависимостей не подтверждена. Читай ошибки и логи, а не только счётчик результатов.

Не обнаруженные этими запусками сценарии: reflected/stored XSS, IDOR, недостаток ограничения входа; собственная CSRF-защита также требует отдельной проверки. Их ручные/динамические доказательства не следует выдавать за находки CodeQL.

### Как открыть SARIF и перейти к строке

1. В VS Code используй расширение **SARIF Viewer**, ID `MS-SarifVSCode.sarif-viewer`, если оно доступно.
2. Для vulnerable открой папку `app/` через **File → Open Folder**; для fixed — `app-fixed/`. В SARIF пути вроде `main.py` относительные, поэтому это помогает правильно найти файл.
3. Открой соответствующий `codeql.sarif` через **File → Open File** и Results Panel расширения. Выбери находку, затем строку/шаг потока данных. Видны rule ID, описание, источник и опасная операция.
4. Если файл не находится, открой его вручную через Ctrl+P и перейди к строке через Ctrl+G. Сам SARIF содержит `ruleId`, `locations` и, где предоставлено, `codeFlows`. Нулевой SARIF fixed не содержит строк для перехода — сравни его с vulnerable и прежним fixed.

## 11. Готовый порядок защиты на 12–15 минут

1. 1 минута: три адреса, схема запроса, `docker compose ps`.
2. 1 минута: обычная заявка, поиск, документ, ping.
3. 5–6 минут: шесть атак из раздела 5; для каждой сравнить 8080 → 8081 → 8082. Stored XSS показать двумя пользователями, IDOR — обоими владельцами.
4. 1 минута: `waf-evidence.json`, реальный rule ID и `lab_case`; пояснить отличие WAF 403 от отказа приложения.
5. 3–4 минуты: результаты стандартного CodeQL vulnerable → код → fixed; отдельно старые три path-находки → новый каталог → ноль; оставшиеся Bandit B404/B603.
6. 1–2 минуты: реальные тестовые JSON, отдельные ограничения SAST, короткий показ лимитера и дополнительных Sonar/Semgrep, если хватает времени.

Сканирования лучше выполнить до занятия. На защите сначала показывай сохранённый результат с датой и версией, затем при необходимости запускай команду заново. Не обещай, что CodeQL уложится в минуту на другом компьютере.

Подготовь скриншоты: три healthy-контейнера; обычная работа; SQLi vulnerable; реальный XSS-диалог; stored-диалог у Бориса; вывод LAB_TEST; маркер traversal; отказ fixed для IDOR; audit с правилом; SARIF vulnerable и сводка fixed; два оставшихся Bandit. Не включай секреты SonarQube.

## 12. Если результат отличается

| Симптом | Что проверить |
|---|---|
| Браузер перенаправил на вход | Сначала войти на этом хосте; проверить отдельный профиль и cookies |
| CSRF 400 на обычной форме | Обновить страницу после входа/выхода; не копировать токен из другого окна |
| 429 при входе | Дождаться Retry-After; перед отдельным опытом доступна команда `lab.ps1 reset-login-limits`, она также пересоздаёт WAF |
| WAF 502 после пересборки | Повторить `lab.ps1 start`, чтобы nginx заново разрешил адрес backend |
| Старое поведение fixed после правки Python | Выполнить сборку через `lab.ps1 start`: код копируется в образ |
| В fixed CodeQL всё ещё показывает три пути | Проверить дату папки: 23:27 — старый SARIF; 23:44 — новый. Затем проверить новую сводку и логи |
| Alert через WAF при открытии старой заявки | Старый комментарий остался в общей БД. WAF не удаляет его; для повторения опыта нужна осознанная очистка |
| В терминале `curl` работает странно | В PowerShell использовать `curl.exe`. Запрос без cookie/CSRF не заменяет действия вошедшего пользователя |
| JSON содержит FAIL или ошибки запуска | Сохранить журнал и выяснить причину. Не заменять его старыми PASS |
