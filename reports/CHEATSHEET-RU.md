# Шпаргалка для устной защиты

| Вопрос | Короткий ответ |
|---|---|
| Какие задания? | Первое — атаки напрямую и через WAF. Второе — SAST, ручной разбор, исправления и повторная проверка. |
| Почему 6 сценариев и 5 классов? | XSS представлен двумя сценариями: reflected и stored. Остальные: SQLi, Command Injection, Path Traversal, IDOR. |
| 8080 и 8081 — разные приложения? | Нет, один backend и одна SQLite. 8081 добавляет reverse proxy ModSecurity + CRS. |
| Что находится на 8082? | Отдельная исправленная реализация с теми же fixtures, отдельная БД, WAF отсутствует. |
| Что такое CRS? | Набор общих правил для детектирования атак. ModSecurity исполняет их и применяет решение блокировки. |
| Почему 403 недостаточно? | Его может вернуть само приложение. Нужна корреляция конкретного запроса с audit, ID и причиной правила. |
| Как доказать SQLi? | Обычный поиск даёт одну карточку, ввод меняет условие SQL и возвращает четыре. В исправленном коде — параметры. |
| Почему SQL-параметры не лечат XSS? | SQL и HTML — разные контексты. Безопасное сохранение не означает безопасное отображение. |
| Reflected против stored? | Первый payload возвращается в ответ на запрос, второй сохраняется и исполняется при последующих просмотрах. |
| Stored XSS зависит от IDOR? | Нет, #1003 — легально общая заявка двух пользователей. |
| Почему очищать комментарии? | WAF может заблокировать новое сохранение, но не удаляет уже существующую запись. |
| Что исправляет Command Injection? | Отсутствие shell, отдельные аргументы, проверка IP. Timeout и non-root — лишь дополнительные ограничения. |
| Как исправить traversal? | Разрешить канонический путь и проверить, что он внутри разрешённого каталога. Простой запрет `../` недостаточен. |
| Почему WAF не лечит IDOR? | Синтаксически корректный запрос не раскрывает бизнес-правила владения. Их проверяет приложение. |
| Hotspot — уязвимость? | Нет, это место, требующее проверки контекста. Подтверждение требует анализа и доказательств. |
| Semgrep ничего не нашёл — безопасно? | Нет. В реальном запуске p/python дал 0, хотя динамические проверки подтвердили уязвимости. |
| Зачем свои правила? | Показать поиск опасных конструкций отдельно от готового набора. Они не ищут специально известные имена файлов/строки. |
| Почему после исправления 1 предупреждение? | Учебное taint-правило консервативно отслеживает путь к send_file и не доказывает корректный выход по abort; ручной разбор и тесты подтверждают containment. |
| Все ли проверки проведены? | Docker работает: 54/54 HTTP, 5/5 audit WAF, 2/2 обычных ping, 55/55 структурных проверок. Прежние 26 локальных, 36 Windows HTTP и 4 Semgrep-запуска сохранены. SonarQube и браузерный JS — не проверены. |

**Адреса:** 8080 напрямую, 8081 WAF, 8082 исправлено, 9000 SonarQube. **Аккаунты:** `alice / Alice-Lab-2026!`, `bob / Bob-Lab-2026!`. **Тикеты:** Алиса 1001, Борис 1002, общий 1003.

**Команды:** `scripts/lab.ps1 start`, `test`, `logs`, `clean-comments`, `reset`, `sonar`, `scan`, `stop`.

**Главное ограничение:** успешная блокировка конкретных запросов не доказывает предотвращение всех вариантов атак. Ни WAF, ни нулевой отчёт SAST не заменяют исправления и проверку поведения.
